Lesson 4 · 15 min

Lifecycle: getTools, toolchange, AbortSignal, and cancellation

A tool is not forever: the page registers it when the function exists and removes it when it leaves the scene. In the 10/16/2026 spec there is no unregisterTool; what removes it is the signal of an AbortController. And the caller can cancel an execution midway. In this lesson you see the whole cycle and the events the browser fires.

Start the lesson

In this lesson you will

  1. 1Registering with a signal and the toolchange event
  2. 2Remove with abort(): the place of the old unregisterTool
  3. 3Cancel an execution: signal in execute and in executeTool
  4. 4toolactivated and toolcancel: native fires them, polyfill doesn't

Goal: register, list, remove with AbortSignal, and cancel an execution, knowing which events the browser fires at each step.

01 · The lifecycle of a tool

Click each step.

Register again when the function comes back (another route, another state)
Chrome docs: window.ontoolactivated and window.ontoolcancel have not been supported since 156. Listen on document.modelContext.

Measured on 10/19/2026: Chromium 156 fires all three events; polyfill 6.0.3 fires only toolchange.

02 · The lifecycle in code

Excerpt from kit/scripts/ciclo.mjs (runs inside the page). Two controllers: one for registration, one for the call.

Simplified excerpt · kit/scripts/ciclo.mjs
const registro = new AbortController();
await mc.registerTool({
  name: 'tarefa_lenta', description: 'Leva 2 segundos. Existe só para ensinar cancelamento.',
  async execute(_, { signal }) {
    return new Promise((ok, falha) => {
      const t = setTimeout(() => ok({ terminou: true }), 2000);
      signal.addEventListener('abort', () => { clearTimeout(t); falha(new DOMException('cancelada', 'AbortError')); });
    });
  }
}, { signal: registro.signal });

const t = (await mc.getTools()).find(x => x.name === 'tarefa_lenta');
const chamada = new AbortController();
setTimeout(() => chamada.abort(), 100);
try { await mc.executeTool(t, {}, { signal: chamada.signal }); }
catch (e) { /* AbortError */ }

registro.abort();   // removes the tool: there is no unregisterTool

Same sequence in both. The difference is in the "eventos" line: only native fires toolactivated and toolcancel.

If execute doesn't listen to signal, canceling rejects the call, but the work keeps going: the setTimeout fires, the fetch completes, the booking happens. For a tool with side effects, check signal.aborted before writing.

03 · Where to register and where to abort

Same rule in any framework: register at the start, abort at the end.

1. Page

Register after the rules are ready and abort on pagehide.

This is what iniciarWebMCP does in the kit.

KitaddEventListener('pagehide', () => pagina.abort(), { once: true })

2. Route

A tool for a single screen exists only while that screen is mounted.

When the route changes: abort() and register the new screen's tools.

3. Component

In React, register in the effect and abort in the cleanup; strict mode mounts twice, and the repeated name would throw InvalidStateError.

The pattern holds for other frameworks; lesson 7 shows the model.

4. Batch

If the third of four fails, the first two are left hanging.

The kit's registrar() uses one controller per batch and aborts everything on failure.

06 · In three sentences

RemoveSignal at registration and abort() when the function goes away; there is no unregisterTool.
CancelSignal in executeTool; the execute listens to its own signal and stops.
Eventstoolchange, toolactivated and toolcancel on document.modelContext; the polyfill fires only the first.
